# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

CodeHelm is a Claude Code plugin made of Markdown: four skills under `plugins/codehelm/skills/`, plus a `README.md` and an MIT `LICENSE`. This repository is both the plugin marketplace (`.claude-plugin/marketplace.json`, marketplace `codehelm`) and the home of the plugin (`plugins/codehelm/.claude-plugin/plugin.json`, plugin `codehelm`). The logo is stored once, as the plugin icon `plugins/codehelm/.claude-plugin/icon.png`, and the README shows that file. Plugin paths can't point outside the plugin folder, so the logo lives there rather than elsewhere in the repo. A replacement must stay a square PNG of 512–2048 px under 2 MB. There is no application code, build or test tooling. Work here means editing skill prompts, their templates, the manifests and the README.

Only `plugins/codehelm/` is distributed. This `CLAUDE.md` is **not**: skills must not depend on it or on any other file outside their own skill directory.

Commands:

- `claude plugin validate ./plugins/codehelm` checks the plugin, and `claude plugin validate .` checks the marketplace. Run both after changing a manifest or the skill layout.
- `claude --plugin-dir ./plugins/codehelm` loads the working copy for one session, to try out skill changes.

## Architecture: a four-phase pipeline with human gates

The skills form a pipeline. Each phase hands off to the next only through Markdown files in the *target* project, never through chat history:

| Skill | Reads | Writes |
| --- | --- | --- |
| `/codehelm:specify` (optional) | a business brief | `docs/specs/<spec-slug>.md`, one per business feature, after approval |
| `/codehelm:plan-tasks` | a spec, a plain request or an existing plan to amend, and the accepted ADRs | `docs/plans/<plan-name>/plan.md`, after approval, and one ADR per accepted decision in `docs/adr/` |
| `/codehelm:implement <plan> [task]` | `plan.md`, the linked spec sections and ADRs | tests first, then code, for exactly one task, plus that task's status line. The plan's approval covers the task. Sets `DONE` only when the engineer accepts the task at its review stop |
| `/codehelm:audit <plan> [task]` | `plan.md`, its linked ADRs, `verification.md`, code, tests | only `verification.md`, without an approval stop, created from `audit/assets/verification.md` on the first run |

Invariants that run through all four skills. Keep them consistent when editing any one of them:

- **Identical ground rules.** Every `SKILL.md` opens with the same "CodeHelm ground rules" paragraph: never create or edit `CLAUDE.md`, never stage, commit, push, switch branches, rewrite history or delete work unless the engineer asks, keep the engineer's uncommitted changes, change an approved spec or plan only with approval, and ask when a project instruction conflicts with these rules. Skills mention `CLAUDE.md` only in this paragraph, because Claude Code already loads it. When you change this paragraph, change it in all four files.
- **Model and effort.** Right after the ground rules, every `SKILL.md` has the same "CodeHelm model and effort" paragraph, kept identical in all four files like the ground rules, because each skill also needs the recommendation of the skill that comes next:

  | Skill | Model | Effort |
  | --- | --- | --- |
  | `/codehelm:specify` | Opus | `high` |
  | `/codehelm:plan-tasks` | Opus | `high` |
  | `/codehelm:implement` | Sonnet | `medium` |
  | `/codehelm:audit` | Opus | `high` |

  - `/codehelm:audit` sets `model: opus` and `effort: high` in its frontmatter. It runs in a fork, where frontmatter covers the whole run.
  - The other skills can't hold a model past the current turn, so a mismatch is a notice, not a stop. A skill compares the model family its system prompt names (Fable, Opus, Sonnet, Haiku) and `${CLAUDE_EFFORT}` with its recommendation, says in one line when either differs, and continues.
  - A handoff lists, after `/clear`, the `/model` and `/effort` commands the next command needs and the session lacks. Before `/codehelm:audit` it lists none.
- **Mandatory STOP points.** Each skill works in phases (A, B, C, ...) with explicit stops, and a skill run without its required argument asks for it and changes no files.
  - `/codehelm:specify` and `/codehelm:plan-tasks` stop for clarification and again for approval before writing files. Each clarification round asks at most five numbered questions, each with options and a recommended answer.
  - `/codehelm:implement` starts directly, because the approved plan covers its task. Given only a plan name, it picks the task whose **Branch** is the current branch, or else the next `NOT STARTED` task whose dependencies are all `DONE`. It stops first only on drift since approval, a branch other than the task's **Branch**, a dependency that isn't `DONE`, a dirty tree, work outside the task's scope, a plan conflict or a failing baseline. It always stops for human review after verification, and after each requested change re-runs the checks and stops again until the engineer accepts.
  - `/codehelm:audit` has no approval stop. It writes only `verification.md`, and ends the run with a question wherever it must ask. Run without a plan name, it audits the only plan under `docs/plans/`, and lists the plans and asks only when there are several.
- **Git and drift.** `/codehelm:implement` and `/codehelm:audit` require a Git repository and stop if there is none. `/codehelm:plan-tasks` asks the engineer to set up Git or commit before approving the plan when the project has no repository, no commit yet or an uncommitted file named in the plan's `Sources` line, then records the commit at approval in the plan's `Approved` line, and implement and audit detect source drift with `git diff <sha> -- <source>`: implement stops, and audit reports it as a finding.
- **Document layout.** One business feature takes a spec pull request, a plan pull request and one pull request per task, each started from the default branch after the ones it depends on merge. CodeHelm only suggests the branches, commits and pull requests.
  - **Spec:** `docs/specs/<spec-slug>.md` on `docs/specify-<spec-slug>`. The slug names a business feature, never a technical layer. When a brief covers several features, `/codehelm:specify` proposes one spec per feature and writes one per run.
  - **Plan:** `plan.md` and its new ADRs on `docs/plan-<plan-name>`. A plan implements one spec and is named after its slug, or more specifically when that plan folder exists. Given an existing plan, `/codehelm:plan-tasks` amends it instead, keeping its name, tasks and statuses; an amendment for a task with uncommitted work ships in that task's commit. `/codehelm:plan-tasks` asks to merge a spec that sits only on an unmerged branch before approving, because a squash merge can drop the commit the plan records. More than about eight tasks is too big for one plan to review and deliver task by task, so it proposes splitting the spec.
  - **Tasks:** each task on its own branch `<type>/<plan-name>-<task-id>` (the type of the task's commit message, the task ID in lowercase), recorded in the task's **Branch** line, with the task's one commit and its status line. Its pull request opens after the engineer accepts the task, and its suggested description links the spec, the plan task and the IDs the task covers. Dependencies merge first, so a dependency's `DONE` reaches the next task's branch through the default branch, and independent tasks can run in parallel. The last task's pull request opens after the full audit finds the change ready for delivery and also carries `verification.md`.
  - A plan with no new ADR and at most two tasks is committed on the first task's branch instead of getting its own pull request, and a plan from a plain request has no spec pull request.
- **Shared vocabulary.** Requirement IDs (`FR-###`, `BR-###`, `NFR-###`, `AC-###`), task IDs (`S01`, `S02`, ...), decision IDs (`ADR-NNNN`, one file per decision at `docs/adr/NNNN-<decision-slug>.md`, numbered across the repository, from `plan-tasks/assets/adr.md` and linked from the plan's Decisions section; only `/codehelm:plan-tasks` writes ADRs, as `Accepted`, and changes an accepted one only to set `Superseded by ADR-NNNN`), assumption IDs (`A-###`) and open-question IDs (`Q-###`, both in `specify/assets/specification.md`), the spec filename placeholder `<spec-slug>` (`docs/specs/<spec-slug>.md`, named after a business feature), the commit trailer `Task: <plan-name>/<task-id>` (the last `-m` of the commit commands `/codehelm:implement` suggests on acceptance; `/codehelm:audit` finds a task's commits with `git log --grep`), the provenance labels `EXPLICIT` / `ASSUMPTION` / `PROPOSED`, the task statuses `NOT STARTED` / `BLOCKED — <reason>` / `READY FOR HUMAN REVIEW` / `DONE` (defined in `/codehelm:implement`, which sets all of them except `NOT STARTED`, set by `/codehelm:plan-tasks`; `/codehelm:audit` checks them against the evidence and never changes them), and the audit statuses `VERIFIED` / `FAILED` / `NOT VERIFIED` / `NOT APPLICABLE` (only `/codehelm:audit` writes `verification.md` and sets them, as only `/codehelm:plan-tasks` writes ADRs). These terms are defined in several skills and in the skills' bundled `assets/` templates, so a rename must be made everywhere.
- **No `PROPOSED` in saved files.** `PROPOSED` marks an unapproved item only while a skill runs. Saved specs and plans contain only `EXPLICIT` and `ASSUMPTION` items: `/codehelm:specify` turns an approved item into an `ASSUMPTION` with an `A-###` entry and an unapproved one into a `Q-###` open question, and `/codehelm:plan-tasks` asks once, in Phase B, making each item an `ASSUMPTION` or moving it out of scope.
- **One plan shape that links the spec.** Each task's **Covers** line links requirement and acceptance criterion IDs. A plan from a spec doesn't copy the spec's requirements: its Requirements table holds only items no spec holds, which is all of them for a plan from a request. Empty sections, such as Decisions or Risks, are omitted. `/codehelm:implement` and `/codehelm:audit` read covered IDs from the spec on the plan's `Sources` line or from the plan's Requirements table.
- **Bundled templates.** The skills bundle `specify/assets/specification.md`, `plan-tasks/assets/plan.md`, `plan-tasks/assets/adr.md` and `audit/assets/verification.md`. Skills refer to their templates as `${CLAUDE_SKILL_DIR}/assets/...` so that they work wherever the plugin is installed. Never point at a path in the target repo such as `docs/templates/`.
- **Plan-level test commands.** `/codehelm:plan-tasks` discovers the target project's complete unit and integration suites and its build or lint command from that project's own configuration and records them in the plan's **Test commands** section, so approving the plan approves them. A project without tests gets a setup task first, unless the engineer approves "no integration tests" once for the whole plan. The plan marks each command that the setup task creates (`(created by S01)`), and that task's baseline skips them. Each task lists only its **Extra checks**. `/codehelm:implement` runs the test commands as a baseline before editing and stops if one fails (a resumed `BLOCKED` task's own failing tests don't count), then runs every test command plus the task's extra checks after implementing. It fixes failures it caused; a missing command or a failure from outside the task sets `BLOCKED`. `/codehelm:audit` runs the same commands when it needs evidence, and reports a suite the changes need that the plan lacks. CodeHelm ships no wrapper scripts and stays language-agnostic.
- All skills set `disable-model-invocation: true`, so they run only when the user invokes them. `/codehelm:audit` also sets `context: fork` with `background: false`, plus `model: opus` and `effort: high`: it runs on that model and effort in a subagent without the conversation history and can't ask questions mid-run, so wherever it must ask, it ends the run with the question.
- **Namespaced command names.** Skills, templates and the README always write commands in the plugin form `/codehelm:<skill>`, including next-command hints.
- **Fresh session between skills.** Skills can't run `/clear`, so a handoff that ends a skill's work ends with a **Next** block, defined in the shared "model and effort" paragraph: one step per line, the exact commit commands, one terse pull request step where one is due, `/clear`, the `/model` and `/effort` switch where needed, then the next command. Why the pull requests come in that order lives once, in the README's Git flow section; skills don't explain it. A blocked `/codehelm:implement` task's block has no commit, because a task gets exactly one commit: only `/clear` and the command that resumes it. A plan with no new ADR and at most two tasks is committed on the new first task's branch; a full audit commits `verification.md` on the current task's branch (or on `docs/audit-<plan-name>` from the default branch) and, once the change is ready for delivery, ends with the last task's pull request. Never suggest `/clear` while a run continues: at implement's review stop, after a task audit (it returns to that review stop) or at a mid-run question.

## Editing conventions

- When you change skill behavior, update `README.md` too (the quick start, the skills table, the rules and the Git flow), and the reverse.
- Users stay on the `version` in `plugins/codehelm/.claude-plugin/plugin.json` until it changes. Bump it (semver) when a release should reach users, and keep the plugin description in `plugin.json` and `marketplace.json` the same. Before a release, check `cat $(git ls-files 'plugins/*.md') | wc -w` against the current word budget (6,250 words).
- Commit messages use Conventional Commits (`feat:`, `docs:`, ...), as in the existing history.
